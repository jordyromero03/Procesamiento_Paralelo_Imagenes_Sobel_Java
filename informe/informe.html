1. Objetivo

Aplicar detección de bordes a una imagen de alta definición descargada de Unsplash, con un tamaño original mayor a 6000 × 6000 píxeles, definiendo la máscara de convolución y repartiendo el trabajo entre varios hilos con Java Threads. Después comparo el tiempo de la versión secuencial con el de la versión paralela usando distintas cantidades de hilos, y calculo la aceleración (speedup) y la eficiencia.

Para el paralelismo uso directamente la clase Thread con start() y join(). No uso ExecutorService, parallelStream() ni bibliotecas de visión como OpenCV: todo el filtro está escrito a mano con la biblioteca estándar de Java.

3. Fundamento: escala de grises y máscaras de Sobel

3.1 Qué es un borde

Un borde es un lugar de la imagen donde la intensidad cambia de golpe, por ejemplo entre la pared clara de un edificio y el cielo. Para encontrarlo no hace falta el color, solo el brillo de cada píxel. Por eso primero convierto la imagen a escala de grises.

3.2 Conversión a escala de grises

Uso la fórmula de luminancia ITU-R BT.601, que da más peso al verde porque el ojo es más sensible a ese color:

Y = 0.299·R + 0.587·G + 0.114·B

El resultado es un arreglo byte[] gris de 9504 × 6336 posiciones (≈ 60 MB), donde cada valor va de 0 (negro) a 255 (blanco).

3.3 Definición de las máscaras

Una máscara (o kernel) es una matriz pequeña de coeficientes. Para cada píxel, la coloco encima de él y de sus 8 vecinos, multiplico cada coeficiente por el valor del píxel que tiene debajo y sumo los 9 productos. Esa operación se llama convolución. Sobel usa dos máscaras de 3 × 3:

Gx (horizontal)
−10+1
−20+2
−10+1
Gy (vertical)
−1−2−1
000
+1+2+1
  • Gx resta la columna izquierda de la derecha: mide cuánto cambia el brillo de izquierda a derecha y resalta los bordes verticales (como los lados de un edificio).
  • Gy resta la fila de arriba de la de abajo: mide el cambio de arriba hacia abajo y resalta los bordes horizontales (como los techos o el horizonte).
  • La fila o columna central tiene peso 2 para darle más importancia a los vecinos directos. Eso suaviza un poco el ruido.
  • Los coeficientes de cada máscara suman 0, así que en una zona de color uniforme el resultado es 0 (no hay borde).

Con los dos valores calculo la magnitud del gradiente, que dice qué tan fuerte es el borde:

G = √(Gx² + Gy²)      (si pasa de 255 se recorta a 255)

En el código las máscaras están definidas así (src/DeteccionBordes.java:19):

static final int[][] GX = {
    {-1, 0, 1},
    {-2, 0, 2},
    {-1, 0, 1}
};

static final int[][] GY = {
    {-1, -2, -1},
    { 0,  0,  0},
    { 1,  2,  1}
};

3.4 Ejemplo numérico

Un vecindario de 3 × 3 con un borde vertical (oscuro a la izquierda, claro a la derecha):

| 10  10  200 |     Gx = (−10 + 200) + (−20 + 400) + (−10 + 200) = 760
| 10  10  200 |     Gy = −(10 + 20 + 200) + (10 + 20 + 200)        = 0
| 10  10  200 |     G  = √(760² + 0²) = 760  →  se recorta a 255 (blanco: hay borde)

Un vecindario uniforme:

| 90  90  90 |      Gx = 0,  Gy = 0,  G = 0  →  negro (no hay borde)
| 90  90  90 |
| 90  90  90 |

Los píxeles del marco exterior (primera y última fila y columna) quedan en negro, porque ahí la máscara no tiene los 9 vecinos completos.

4.2 Versión secuencial

Un solo hilo (el principal) recorre todas las filas interiores de la imagen, de la 1 a la alto − 2, y aplica las dos máscaras a cada píxel. La lógica está en el método sobelFilas (src/DeteccionBordes.java:105), que recibe el rango de filas que debe procesar: 

static void sobelFilas(byte[] gris, byte[] salida, int ancho, int filaInicio, int filaFin) {
    for (int y = filaInicio; y < filaFin; y++) {
        for (int x = 1; x < ancho - 1; x++) {
            int gx = 0;
            int gy = 0;
            for (int ky = -1; ky <= 1; ky++) {
                for (int kx = -1; kx <= 1; kx++) {
                    int pixel = gris[(y + ky) * ancho + (x + kx)] & 0xFF;
                    gx += pixel * GX[ky + 1][kx + 1];
                    gy += pixel * GY[ky + 1][kx + 1];
                }
            }
            int magnitud = (int) Math.sqrt((double) gx * gx + (double) gy * gy);
            salida[y * ancho + x] = (byte) Math.min(255, magnitud);
        }
    }
}

En la versión secuencial se llama una sola vez con todas las filas: sobelFilas(gris, salida, ancho, 1, alto - 1). No se crea ningún Thread. Así es una referencia limpia para comparar.

En total son 9502 × 6334 ≈ 60.2 millones de píxeles, y cada uno necesita 18 multiplicaciones (9 por máscara): ≈ 1080 millones de multiplicaciones por pasada.

4.3 Versión paralela: descomposición de dominio por filas

La idea es repartir la imagen en franjas horizontales de filas seguidas, una por hilo, como si varias personas pintaran una pared y cada una se encargara de una franja. Todos los hilos ejecutan el mismo método sobelFilas; lo único que cambia es el rango de filas. 

 Imagen 9504 × 6336 (filas interiores 1 .. 6334), ejemplo con 4 hilos

 ┌──────────────────────────────────────┐  fila 1
 │  sobel-0   filas    1 .. 1583        │
 ├──────────────────────────────────────┤
 │  sobel-1   filas 1584 .. 3167        │      cada hilo lee 1 fila extra arriba y abajo
 ├──────────────────────────────────────┤      (solo lectura), pero escribe
 │  sobel-2   filas 3168 .. 4750        │      únicamente en sus propias filas
 ├──────────────────────────────────────┤
 │  sobel-3   filas 4751 .. 6334        │
 └──────────────────────────────────────┘  fila 6334

Los pasos son:

  1. Dividir: calculo el inicio y el fin de cada franja para que todas tengan casi el mismo número de filas (con 8 hilos, 791 o 792 filas cada uno).
  2. Asignar: a cada franja le corresponde un Thread con un objeto TrabajadorSobel (implementa Runnable) que guarda su rango.
  3. Ejecutar: arranco todos los hilos con start().
  4. Esperar: el hilo principal llama a join() sobre cada uno. Funciona como una barrera: no sigue hasta que todos terminan.
  5. Comprobar: comparo la salida con la secuencial con Arrays.equals.

El reparto y la creación de hilos (src/DeteccionBordes.java:124):

static void sobelConHilos(byte[] gris, byte[] salida, int ancho, int alto, int numeroHilos)
        throws InterruptedException {
    int filasInteriores = alto - 2;
    Thread[] hilos = new Thread[numeroHilos];

    for (int i = 0; i < numeroHilos; i++) {
        int inicio = 1 + (int) ((long) i * filasInteriores / numeroHilos);
        int fin = 1 + (int) ((long) (i + 1) * filasInteriores / numeroHilos);
        hilos[i] = new Thread(new TrabajadorSobel(gris, salida, ancho, inicio, fin), "sobel-" + i);
        hilos[i].start();
    }
    for (Thread hilo : hilos) {
        hilo.join();   // barrera: esperar a que todos terminen
    }
}

Y la tarea de cada hilo (src/DeteccionBordes.java:141):

static class TrabajadorSobel implements Runnable {
    ...
    @Override
    public void run() {
        sobelFilas(gris, salida, ancho, filaInicio, filaFin);
    }
}

Uso (long) i * filasInteriores para que la multiplicación no se desborde en imágenes muy grandes, y calculo el fin del hilo i con la misma fórmula que el inicio del hilo i + 1. Así no queda ninguna fila sin procesar ni ninguna fila procesada dos veces.

4.4 Por qué no hace falta synchronized

Una condición de carrera aparece cuando dos hilos escriben en la misma posición de memoria, o uno escribe mientras otro lee. En este programa eso no pasa:

  • El arreglo gris es de solo lectura: todos los hilos lo leen y ninguno lo modifica. Por eso un hilo puede leer sin problema la fila de la franja vecina.
  • En el arreglo salida, cada hilo escribe solo en sus propias filas. Ningún píxel es escrito por dos hilos.
  • join() garantiza que el hilo principal ve todo lo que escribieron los hilos (relación happens-before del modelo de memoria de Java) antes de comparar o guardar.

Poner synchronized dentro del bucle no aportaría seguridad y obligaría a los hilos a turnarse en cada píxel, lo que eliminaría el paralelismo.

5. Metodología de medición

  • Qué se mide: solo el filtro Sobel. La lectura del JPEG, la conversión a gris y la escritura de los PNG quedan fuera, porque no son lo que se está paralelizando.
  • Calentamiento del JIT: Java empieza interpretando el código y lo compila a código nativo cuando detecta que se usa mucho. Si midiera la primera ejecución, la versión secuencial (que va primero) saldría más lenta de lo real y la aceleración se vería inflada. Por eso cada configuración se ejecuta 3 veces sin medir antes de tomar tiempos.
  • Repeticiones: después mido 5 veces con System.nanoTime() y uso la mediana, que no se deja arrastrar por una ejecución lenta aislada.
  • Configuraciones: secuencial (sin hilos) y 1, 2, 4, 8 y 16 hilos.
  • Verificación: cada salida paralela se compara píxel a píxel con la secuencial.

Fórmulas:

Speedup      S = T_secuencial / T_paralelo
Eficiencia   E = S / N × 100 %        (N = número de hilos)

8. Análisis

8.1 Hasta 8 hilos la aceleración crece casi en línea recta

Con 8 hilos el filtro pasa de ≈ 590 ms a ≈ 76–90 ms (speedup entre 6.5× y 7.7×). El equipo tiene 8 núcleos físicos, así que cada hilo ocupa su propio núcleo y trabajan de verdad al mismo tiempo. Esto funciona tan bien porque el problema es muy fácil de dividir: los píxeles no dependen unos de otros, solo leen datos que nadie modifica (un problema "embarazosamente paralelo").

8.2 De 8 a 16 hilos casi no mejora

Con 16 hilos el tiempo es prácticamente igual que con 8 y la eficiencia cae a ≈ 47 %. Hay dos razones:

  • Hyper-Threading: los 16 procesadores lógicos son 8 núcleos físicos, cada uno con 2 hilos de hardware que comparten las mismas unidades de cálculo. Cuando los dos hilos hacen la misma cuenta (multiplicaciones y sumas), se estorban y la ganancia es muy pequeña.
  • Ancho de banda de memoria: cada pasada lee ≈ 60 MB de gris y escribe ≈ 60 MB de salida. Con muchos hilos, la memoria RAM ya no entrega los datos tan rápido como los núcleos los procesan.

8.3 Un hilo es igual o más lento que el secuencial

Con 1 hilo el trabajo es exactamente el mismo, pero además hay que crear el Thread, arrancarlo y esperarlo con join(). Por eso el speedup queda alrededor de 1× (0.95× y 1.06× en las dos ejecuciones). Muestra el costo fijo de usar hilos.

8.4 Eficiencias mayores al 100 %

Con 2 hilos salió una eficiencia de 117.6 % en una ejecución. No es una aceleración superlineal real: es variación de medición. El procesador ajusta su frecuencia (Turbo Boost) según la carga y la temperatura, la caché se comporta distinto con menos datos por núcleo y el sistema operativo tiene otros procesos. En la otra ejecución el mismo caso dio 107 %. Por eso no tomo un número aislado, sino la tendencia.

8.5 Ley de Amdahl: la parte que no se paraleliza

La conversión a escala de grises tarda ≈ 990 ms y se hace con un solo hilo. Es más lenta que el propio filtro Sobel secuencial. Si tomo las dos fases juntas:

FaseSecuencial (ms)Con 8 hilos (ms)
Escala de grises (no paralelizada)989.8989.8
Sobel589.776.3
Total1579.51066.1

El filtro se aceleró 7.7×, pero estas dos fases juntas solo 1579.5 / 1066.1 ≈ 1.48×. Es la ley de Amdahl: la parte secuencial (aquí ≈ 63 % del tiempo) limita la aceleración total, sin importar cuántos hilos se agreguen al resto. La mejora natural sería paralelizar también la conversión a gris con el mismo reparto por filas.

9. Correcciones a la primera versión del código

Partí de una primera propuesta de código que ya usaba Sobel y repartía filas entre hilos. Al revisarla encontré varios problemas y los corregí:

Problema en la primera versiónPor qué era un problemaCómo lo resolví
synchronized (salida) en cada píxel Los hilos se turnaban para escribir: se perdía el paralelismo. No hacía falta porque cada hilo escribe en filas distintas. Lo quité y escribo en un byte[] con zonas separadas por hilo.
Medía la primera ejecución, sin calentamiento El JIT todavía no había compilado el código y la versión secuencial salía más lenta, lo que inflaba el speedup. 3 ejecuciones de calentamiento y mediana de 5 mediciones.
La "versión secuencial" creaba un Thread No era una referencia secuencial pura. Secuencial = bucle normal sin hilos; el caso de 1 hilo se mide aparte.
Probaba un solo número de hilos No se podía ver cómo crece la aceleración ni dónde se estanca. Pruebo 1, 2, 4, 8 y 16 hilos.
No comprobaba el resultado No había evidencia de que la versión paralela calcule lo mismo. Comparación con Arrays.equals en cada configuración.
Escribía en la imagen con setSample píxel a píxel Más lento y más difícil de razonar sobre concurrencia. Escribo en un arreglo y lo copio a la imagen una sola vez al guardar.

10. Conclusiones

  • La detección de bordes con Sobel se paraleliza muy bien: cada píxel se calcula de forma independiente leyendo datos que no cambian, así que basta con repartir filas entre hilos.
  • Con 8 hilos (uno por núcleo físico) el filtro fue entre 6.5 y 7.7 veces más rápido que la versión secuencial, con eficiencias entre 82 % y 97 %.
  • Más hilos que núcleos físicos no ayudan: con 16 hilos el tiempo apenas cambia y la eficiencia baja a la mitad.
  • No hizo falta sincronización, porque los datos de entrada son de solo lectura y cada hilo escribe en su propia zona. join() fue la única coordinación necesaria.
  • La salida paralela fue idéntica a la secuencial en todas las configuraciones: el paralelismo no cambió el resultado.
  • Para medir bien en Java hay que calentar el JIT y repetir las mediciones; si no, los números engañan.
  • La parte que no se paraleliza (la conversión a gris) limita la mejora total del programa, como predice la ley de Amdahl.
